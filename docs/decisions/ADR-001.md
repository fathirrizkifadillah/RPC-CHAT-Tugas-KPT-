# ADR-001: In-Memory Concurrency and Message Queue Architecture

## Status
Accepted

## Date
2026-10-29

## Context
Sesuai rancangan arsitektur pada diagram `arsitektur-chat-room.svg` dan spesifikasi akademis PDF Praktikum RPC (Halaman 12–13), server chat harus mampu menangani banyak client bersamaan (hingga 20 client konkuren) tanpa terjadi *race condition* atau kerusakan data.

Sistem tidak boleh menggunakan message broker eksternal (seperti Redis, RabbitMQ, Kafka) atau database SQL/NoSQL agar implementasi terfokus pada konsep inti Remote Procedure Call (RPC) dan *concurrency control* pada memori bersama (*shared state*).

Komponen shared state yang ditetapkan adalah:
1. `users`: Daftar pengguna aktif.
2. `queue`: Antrean pesan per client aktif.
3. `PROSES`: Penyimpanan hasil pemrosesan request untuk deduplikasi.

## Decision
1. **Model Concurrency Server**:
   Server gRPC menggunakan `concurrent.futures.ThreadPoolExecutor(max_workers=30)` untuk melayani RPC handlers secara konkuren.

2. **Sinkronisasi Shared State (`ChatState`)**:
   - Seluruh shared state dibungkus dalam modul domain `ChatState`.
   - Menggunakan `threading.RLock` terlokalisasi (reentrant lock) untuk melindungi mutasi dictionary `users`, `queues`, dan `PROSES`.
   - **Critical Section Minimal**: Lock HANYA dipegang saat memutasi dictionary internal dan menyalin snapshot (`shallow copy`). Lock TIDAK PERNAH dipegang saat melakukan I/O jaringan atau menunggu antrean.

3. **Isolasi Antrean Per Client (`queue.Queue`)**:
   - Setiap client yang terhubung ke bidirectional stream `Chat` memiliki instance `queue.Queue(maxsize=100)`.
   - Publisher (pengirim pesan) menaruh frame pesan ke antrean setiap client aktif secara non-blocking (`put_nowait`).
   - Jika antrean client tertentu penuh (*slow client*), server mencatat peringatan dan membuang frame tertua (*drop oldest*) atau menjatuhkan pesan untuk client tersebut tanpa mengganggu atau memblokir pengirim maupun client lainnya (*slow client isolation*).

4. **Siklus Hidup dan Pembersihan (Cleanup)**:
   - Ketika stream terputus (`context.is_active() == False` atau frame LEAVE diterima), callback pembersihan menghapus client dari `users` dan membuang `queue` terkait.
   - Server membroadcast event bahwa pengguna telah keluar ke seluruh client yang tersisa.

## Consequences
- **Positif**: Bebas race condition, latensi minimal karena lock tidak memblokir antrean atau jaringan, isolasi client lambat mencegah *head-of-line blocking*.
- **Trade-off**: Karena berada di memori, state bersifat volatil (hilang bila server restart). Ini didokumentasikan sebagai karakteristik arsitektur in-memory RPC.
