# ADR-002: Request-ID Deduplication and Semantics of Unary vs Streaming RPC

## Status
Accepted

## Date
2026-10-29

## Context
Pada jaringan terdistribusi, kegagalan parsial sering terjadi: paket respons dapat hilang atau terlambat meskipun server telah mengeksekusi operasi (misal timeout pada client). Jika client mencoba ulang (*retry*) operasi pengiriman pesan tanpa pengaman, pesan yang sama dapat dikirim dan dibroadcast berulang kali (duplikasi pesan).

PDF praktikum mensyaratkan:
- Operasi yang tidak idempoten wajib dilindungi ID permintaan (`request_id`).
- Server harus mengimplementasikan semantik *at-most-once* menggunakan pencatatan `PROSES`.
- Terdapat 4 RPC: `Join`, `ListUsers`, `SendMessage`, `Chat`.

## Decision
1. **Peran `PROSES` dalam Deduplikasi**:
   - `PROSES` menyimpan pemetaan `request_id -> ResponsePayload`.
   - Sebelum memproses pesan atau registrasi, server memeriksa apakah `request_id` telah ada di `PROSES`.
   - Jika ditemukan (`hit`), server mengembalikan respons yang tersimpan secara instan tanpa melakukan broadcast ulang ke client lain.
   - Jika baru (`miss`), server memproses permintaan, membroadcast pesan ke seluruh antrean client, menyimpan hasilnya ke `PROSES`, lalu mengembalikan respons sukses.

2. **Hubungan Unary `SendMessage` vs Bidirectional Streaming `Chat`**:
   - `SendMessage` (Unary RPC): Dirancang untuk pengiriman pesan independen dengan respons langsung (ACK) yang sangat cocok untuk operasi request-reply terisolasi dan pengujian retry/timeout eksplisit.
   - `Chat` (Bidirectional Streaming RPC): Dirancang sebagai jalur interaktif utama untuk pengalaman chat real-time, di mana client membuka satu koneksi stream panjang untuk mengirim pesan dan menerima pesan masuk secara simultan.
   - **Logika Broadcast Terpadu**: Baik pesan yang dikirim lewat `SendMessage` maupun frame yang dikirim lewat `Chat` menggunakan engine publikasi yang sama pada `ChatState`, sehingga pesan dari Unary RPC langsung muncul pada stream client lain, dan kedua jalur dilindungi deduplikasi `request_id` yang sama.

## Consequences
- Mencegah pesan duplikat saat terjadi retry jaringan.
- Memenuhi persyaratan at-most-once semantics.
- Kapasitas memori `PROSES` dikelola dengan batas retensi/LRU sederhana jika mencapai batas tertentu untuk mencegah kebocoran memori jangka panjang.
