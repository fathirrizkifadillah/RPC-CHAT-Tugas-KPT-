# ADR-003: Client Retry and Exponential Backoff Strategy

## Status
Accepted

## Date
2026-10-29

## Context
Client RPC yang beroperasi pada jaringan terdistribusi harus tahan terhadap gangguan jaringan sementara (*transient failures*), beban puncak, atau server restart singkat. Modul praktikum halaman 10–11 menjelaskan pentingnya timeout dan retry dengan jeda eksponensial (*exponential backoff*).

Namun, melakukan retry secara sembarangan terhadap semua jenis error (seperti `INVALID_ARGUMENT` atau `ALREADY_EXISTS`) adalah anti-pattern yang dapat memperburuk beban server (*retry storm*).

## Decision
1. **Pemilihan Error Code yang Boleh Di-retry**:
   Client HANYA mengulang pemanggilan jika status kode gRPC tergolong transient:
   - `grpc.StatusCode.DEADLINE_EXCEEDED` (timeout pada RPC)
   - `grpc.StatusCode.UNAVAILABLE` (server sedang sibuk atau restart)
   - `grpc.StatusCode.RESOURCE_EXHAUSTED` (antrean sementara penuh)
   Untuk error deterministik seperti `INVALID_ARGUMENT`, `NOT_FOUND`, atau `ALREADY_EXISTS`, client langsung melempar error tanpa retry.

2. **Konsistensi `request_id` pada Setiap Percobaan**:
   - Client menghasilkan satu UUID `request_id` unik pada awal pemanggilan sebuah operasi logis.
   - Pada percobaan ke-1, ke-2, hingga batas maksimum (`max_retries=3`), nilai `request_id` yang sama persis dikirimkan ke server.
   - Client DILARANG membuat UUID baru saat retry karena akan menggagalkan mekanisme deduplikasi server.

3. **Algoritma Backoff**:
   - Base delay: 0.5 detik.
   - Exponential formula: `delay = base_delay * (2 ** (attempt - 1)) + random_jitter`.
   - Adanya jitter acak kecil mencegah thundering herd problem bila banyak client melakukan retry bersamaan.

## Consequences
- Client tangguh terhadap kegagalan sementara tanpa membebani server secara destruktif.
- Idempotesi terjaga penuh melalui kombinasi stable `request_id` dan in-memory cache `PROSES`.
